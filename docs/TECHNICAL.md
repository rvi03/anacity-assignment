- **Traditional / CatBoost** — below.

## Traditional track

### What this chapter may and may not claim

Everything below was measured. Where a number is an estimate it says so.

**May claim.** A frequency/recency baseline and four CatBoost heads, both
scored on a chronologically later holdout that was read exactly once.
Leakage controls asserted per row on every run, and independently
verified by a property test and a negative control. A reproducible
pipeline: same seed, same digests, same numbers.

**May not claim.** That the model beats the baseline. On the holdout it
**ties** it. That is the headline result and it is not buried.

### The problem, as scored

Given a resident and a moment in time, predict four things about their
next booking: which facility, which weekday, which hour, and how long
after the moment they will make the booking. A prediction "matches" on
each component independently; the notification component matches when the
predicted delay lands inside ±25% of the actual.

The headline number is the mean of the four match rates. The same number
selects between models and leads the report, so the selection procedure
cannot pick a model that scores worse on what is reported.

### Data

500 residents, 24 months, 8 facilities, **21,442 bookings**, generated
from a seeded simulation. The generator carries hidden structure the
model must rediscover: per-resident archetypes and preferences, an
activity distribution, capacity limits, and three dated drift events —
a facility that opens late and takes demand from another, a share of
residents who change habits outright, and one facility with a seasonal
swing.

None of that hidden state reaches the modelling table. 18 acceptance
checks assert each property is actually present, and they run inside
`make all` rather than only in tests.

### From bookings to prediction rows

Each row is a **rolling origin**: the moment a resident's previous
booking was created, predicting their next one. That gives **20,948**
rows from 21,442 bookings. Residents with no prior history are excluded
and counted, not dropped silently.

The split is chronological on elapsed time, 70/15/15:

```
train        13,915 rows   2024-01-02 → 2025-05-24
validation    3,437 rows   2025-05-24 → 2025-09-10
holdout       3,596 rows   2025-09-10 → 2025-12-28
```

### Features

**161 columns**, 7 categorical and 154 numeric, in three families:

- **Origin** — calendar position of the moment itself.
- **Resident history** — counts and rates over 7/30/90/180-day windows,
  the rolling favourite facility over the last 3/5/10 bookings, time-band
  shares, inter-booking intervals, exponentially decayed preference at a
  30-day half-life, entropy, and transition counts.
- **Community history** — what everyone else did, over 30 and 90-day
  windows ending strictly before the origin.

Missing categorical values carry an explicit `__MISSING__` token rather
than a blank, so "no history yet" is a value the model can learn from
instead of a hole.

### Leakage controls

This is the part a reviewer should be most suspicious of, so it gets the
most machinery. Six numbered controls, each with tests that fail if the
control is removed:

| | Control | How it is enforced |
|---|---|---|
| L1 | Resident history ≤ origin; target > origin | asserted **per row, every run** — 20,948 rows over 903,547 events |
| L2 | No target or target-derived column is an input | manifest diffed against a denylist, 0 violations over 161 columns |
| L3 | Community windows stop strictly before the origin | `closed='left'` asserted on every rolling call, over 220,232,404 events |
| L4 | The split is chronological and cannot overlap | boundary assertions |
| L7 | Split membership is frozen and cannot reach a fit | fit-call audit: 13,915 rows, all training |
| L8 | Generator hidden state never reaches the model table | column-set assertion |

L6 governs chained models, which do not exist here. It is absent and
nothing is claimed about it.

Two further verifications look for the *effect* of a leak rather than
asserting a rule:

- **Future perturbation** — change or delete bookings after a row's
  origin; every feature of that row must be byte-identical. Cases are
  generated by Hypothesis over timezone-aware instants.
- **Shuffled-label control** — break the link between features and
  target, fit, and score on rows the fit never saw. No head may beat its
  own majority-class prior by more than sampling noise.

Both carry a sensitivity check, because a blind instrument passes
everything: the perturbation test proves the same edit *does* move a row
it is allowed to move, and the negative control proves it fires when a
target is planted in the feature matrix.

### Models

**Baseline** — per-resident frequency and recency, with an order-1
Markov transition on the last facility, falling back to community
behaviour where a resident has no history. It is not a strawman. It is
the thing to beat, and it is hard to beat because most of the signal in
this problem is one resident repeating themselves.

**CatBoost** — four heads over the same feature table.

| Output | Estimator | Iterations kept |
|---|---|---:|
| Facility | MultiClass classifier | 144 |
| Weekday | MultiClass classifier | 100 |
| Hour | MultiClass classifier | 18 |
| Notification | **bucket** classifier | 129 |

Two decisions are worth explaining.

**The notification head is not a regression.** It was one, and it was
the worst part of the model: 0.095 against a scored rule that a single
global constant satisfies 0.111 of the time. The cause was an
objective/metric mismatch — minimising minute-space error optimises a
different quantity from a ±25% tolerance window, and on a
right-skewed delay distribution its optimum sits where almost no window
is hit. Every regression framing was measured and rejected: `MAE` and
`RMSE` on raw and log targets, and `SurvivalAft`, all scored 0.054–0.072.
The head now classifies delay buckets narrow enough to fit inside the
tolerance window, and decodes by the heaviest **window** rather than the
heaviest bucket. That took it to **0.131** on validation, above the
baseline's 0.127.

**The iteration count is searched, not fixed.** One count shared by
heads that separate 7, 8 and 24 classes is a guess. Each head cuts the
latest 15% of the *training* rows as an inner fold, takes the best count
there, then refits on all training rows at that count. No validation or
holdout row takes part, the kept fit is passed no evaluation set, and
`use_best_model` stays false — so the shipped model has no early
stopping and the selection claim is untouched.

**Per-output selection.** The baseline and CatBoost are both eligible to
supply each output. On validation only, the stronger source is chosen per
output and frozen before the holdout is touched:

```
facility     CatBoost
weekday      baseline
hour         CatBoost
notification CatBoost
```

This composes already-generated predictions. It is not blending and it
does not mix splits. Every candidate is still reported separately, so
the composite cannot hide a weaker head.

### The freeze, and one scoring

The holdout is scored **once, ever**. Two records enforce it: a freeze
written before any holdout row is read, carrying the configuration hash
and the source map; and a seal written after. Scoring refuses if the
configuration moved after the freeze, and refuses outright if the seal
already exists. The refusal message states what deleting the seal would
cost — every subsequent number becomes a best-of-N result.

### Results

**Holdout, 3,596 rows, scored once.**

| | Selected heads | CatBoost alone | Baseline |
|---|---:|---:|---:|
| Facility | 0.3757 | 0.3757 | **0.3765** |
| Weekday | 0.2845 | 0.2764 | 0.2845 |
| Hour | 0.2036 | 0.2036 | **0.2041** |
| Notification | **0.1204** | 0.1204 | 0.1190 |
| **Overall** | **0.2460** | 0.2440 | **0.2460** |

The selected heads and the baseline **tie**, to the last decimal place
the data supports. It is a real tie and not a bug: the baseline wins
facility by 3 rows and hour by 2, the selected heads win notification by
5, and the two cancel exactly.

CatBoost alone **loses**, 0.2440 against 0.2460.

Also measured: notification MAE 16,369 min against the baseline's 16,402
(a 0.2% reduction, clamp rate 0), facility macro-F1 0.3465 against
0.3394, hour-within-1-hour 0.5225 against 0.5086, all four components
correct on 0.44% of rows, three or more on 3.95%.

**Validation, for contrast.** The selected heads scored 0.2401 against
the baseline's 0.2320 and CatBoost alone 0.2397. The lead on validation
did not survive to the holdout. That gap is the most useful number in
this document: it is what tuning against a split looks like when you then
measure honestly.

### Where it fails

18 slices over 7 dimensions, each asserted to partition the holdout:

- **The thin end of the catalog.** Facility accuracy 0.2877 on the
  less-popular half against 0.4038 on the popular half.
- **Weekdays, not weekends.** 0.2197 against 0.2692.
- **Not cold start.** Residents never seen in training score 0.2593
  against 0.2396 for those that were. Cold start is not the weakness
  here, which is what a mostly-community signal predicts.
- **The largest single error mode is the drift event itself** — Yoga
  Room predicted as Gym, 164 rows. Yoga Room is the late-opening
  facility that takes Gym's demand.

Feature importance is reported two ways, gain and SHAP over a fixed
seeded 500-row sample, because they answer different questions and
averaging them would hide where they disagree.

### Alternatives considered

| Considered | Outcome |
|---|---|
| Notification as `MAE`/`RMSE` regression, raw and log target | **Measured and rejected**: 0.054–0.072, below a global constant |
| `CatBoost SurvivalAft` on the delay | **Measured and rejected**, same range |
| Facility head as a learning-to-rank problem (`YetiRank`) | Built and configurable; 0.3561–0.3614 on validation against 0.3526 — **within noise** (SE ≈ 0.008), so it ships off by default |
| Notification framed around each resident's own booking cadence | Built and configurable; ships off by default, reported as a declared alternative |
| Exponential recency weights on preference | Measured and rejected, worse at every half-life tried |
| Reconstructing the usage timestamp from gap plus lead | Measured and rejected: weekday 0.1365, hour 0.0361 |
| Order-1 Markov on the last facility as the primary facility rule | Measured and rejected: 0.3228 against 0.3524 for a plain personal mode |
| `has_time=True` on CatBoost | Measured and rejected: facility 0.3518 → 0.3486 |
| Sequential recommenders (SASRec, BERT4Rec) | **Deliberately skipped and documented as skipped**: defensible on paper, both break the "reviewer runs it in minutes" constraint |
| Neural temporal point processes | Same |
| An LLM track | Built as a separate branch; see the chapter below |

A leave-one-out per-resident oracle scores 0.3791 / 0.2732 / 0.2040 on
facility / weekday / hour. The three classifier heads already sit at or
above a static personalised ceiling, which is a large part of why the
margin over the baseline is thin.

### After the freeze: registry and stretch variants

Once the holdout is spent, two things happen that cannot change what
shipped.

**The frozen heads are registered.** Each of the four is attached to a
run and registered as a named version tagged `frozen` with the
configuration hash it was fitted under, so "the model that produced this
number" resolves to bytes rather than to a file path someone remembers.

**A single cross-track query** scores every track over the same seeded
500-row comparison subset — the thing that subset exists for. A track
with no rows on it is reported with a zero count rather than dropped by
the join, because a track that has not run is a fact about the project
and not an absence to hide.

| Track / model | Overall on the 500-row subset |
|---|---:|
| traditional / selected heads | 0.2545 |
| traditional / CatBoost | 0.2540 |
| baseline / frequency-recency | 0.2510 |
| llm / adapter | 0.2185 |

On this subset the selected heads lead. On the full holdout they tie.
The subset is not the headline and is not reported as one.

**Stretch variants** run last, on validation only, under two ceilings:
a declared fit budget and a wall-clock budget. The run works the plan's
priority order top-down and stops at the first variant it cannot afford
— stopping on cost rather than on results is what keeps the stopping
point a rule rather than a choice. The wall-clock ceiling exists because
a fit count alone does not bound anything here: the cadence notification
framing has 60 residual classes and costs an order of magnitude more
than a classifier refit.

Nothing in that run writes a model, a prediction row, or `metrics.json`.
It writes one report, which records what ran, what the budget stopped
before, and what was never built at all.

All 12 declared fits ran, in 8 minutes:

| Variant | Head | Variant | Frozen |
|---|---|---:|---:|
| Notification cadence framing | notification | 0.1266 | 0.1312 |
| Notification argmax decode | notification | 0.1271 | 0.1312 |
| Facility ranking framing | facility | 0.3521 | 0.3599 |
| Depth 8 | facility | 0.3515 | 0.3599 |
| Learning rate 0.03 | facility | **0.3619** | 0.3599 |
| L2 = 20 | facility | **0.3666** | 0.3599 |

Two variants beat the frozen facility head on validation. **Neither was
adopted.** The configuration is frozen and the holdout is spent; taking
a winner now would make every holdout number a best-of-N result, which
is exactly what scoring once is meant to prevent. They are reported as
what they are — evidence about what a next iteration should try.

A methodology error is worth recording, because it changed the numbers.
The first implementation ran a fresh iteration search inside each
variant, which made every comparison two factors at once — the setting
under test and a different tree count — and cost 101 CPU-minutes on the
first variant before producing anything. Each variant is now fitted at
the tree count of the head it replaces, which is what §9.6's
"one-factor neighbours" asks for and what made the whole list affordable.

### Testing

735 tests. Categories, not counts, are what matters: unit tests for every
metric with hand-checked fixtures including boundary and
zero-denominator cases; leakage controls; storage and layering; the two
Band-B verifications; determinism; and tests that break each consistency
gate to prove it fires.

`make verify` recomputes every committed value — input digests, the
configuration hash, both splits' metrics, the workbook hash, and the
experiment tracker's headline metrics — and reports differences rather
than repairing them. 22 tests break one committed value each and confirm
the check catches it.

### Limitations

- **The model ties the baseline on unseen data.** Everything above is
  reported against that.
- The dataset is synthetic. Every result is a statement about a
  simulation whose structure was chosen, not about a real community.
- The notification component is quantised into buckets, so its ceiling
  is structural, not just modelling.
- One holdout scoring means no confidence interval on the holdout
  numbers from repeated evaluation. The interval reported is a bootstrap
  over rows, not over runs.
- L6 (chained heads) is untested because chained heads do not exist.
- The generator has a measured bias: Clubhouse realises 0.1196 against
  0.09 configured, and the bootstrap interval excludes the configured
  value. That is a property of the simulation, reported rather than
  tuned away.

## LLM track

### What this chapter may and may not claim

This branch was built **spine-first**: it started once the shared data,
split, feature, metric, and baseline modules existed, rather than waiting
for the traditional track to finish and freeze. That was a recorded
deviation, and while it stood it barred this chapter from three claims.
The traditional track has since completed and frozen, so the bar has
lifted — but nothing here depends on that, because the branch was measured
against the shared **frequency/recency baseline** throughout and still is.

This chapter claims **no verification band of its own**. The band on the
repository is the traditional track's and is stated in its chapter. What
follows is one number, honestly placed: a fine-tuned local model scored
once on the same frozen holdout rows as every other model, using metric
definitions imported from the shared evaluation module rather than
redefined here.

**Leakage in this branch is *asserted*, not *proven*.** The proof
machinery — future perturbation, shuffled-label control — belongs to the
traditional track and covers the shared feature path, not the prompt path.

### The problem, as this track frames it

Four outputs are predicted from a resident's booking history at a fixed
prediction origin: which facility, which weekday, which hour, and how long
until they make the booking. The first three are exact-match questions. The
fourth is scored by a symmetric ±25% multiplicative window, so it is a
question about magnitude, not about a minute.

A language model answers all four in one constrained JSON object.

```
  resident history at the origin
            │
            ▼
  rendered prompt (summaries + recent bookings + the allowed label set)
            │
            ▼
  4-bit Qwen3-4B + LoRA adapter, greedy, schema-constrained
            │
            ▼
  {"facility", "usage_day", "usage_hour", "notification_delay_bucket"}
            │
            ▼
  bucket → its representative minute count → the shared ±25% test
```

### Representation: why the delay is a bucket

A language model that emits free-form minute counts cannot be constrained
to a finite, auditable answer space, and its errors are unbounded. So the
delay is discretised before any model sees it.

The edges are **cut to the metric, not to round numbers**. The scored test
accepts anything within ±25% of the answer, a total multiplicative width of
1.25² = 1.5625. A finite bucket is therefore given a width of 1.5, which is
narrow enough that its **geometric midpoint** covers the whole bucket: a
model that names the right bucket is guaranteed a match. Round-number
edges — "under 6 hours", "1 to 2 days" — would have capped the LLM's
notification score well below 1.0 while a regressor faced no such cap. That
would have been an artefact of the representation rather than a modelling
result.

Buckets are built from **training rows only**, and any bucket with fewer
than 200 training rows is merged into a neighbour until none is left thin.
That produced **17 labels after 5 merges**, forming a contiguous partition
of `[0, ∞)` with two unbounded ends.

The cost of the discretisation is measured, not assumed. A *perfect* bucket
classifier scores **0.9545** on the notification test — the two unbounded
ends carry all of the loss, since every finite bucket is covered end to end.
That number is the ceiling this representation imposes, and every trained
result below is measured against it as well as in absolute terms.

### Prompt

One template, hashed and versioned. It carries, for each row:

- the prediction origin and the allowed facility names;
- the full allowed label set with each bucket's numeric range, so the model
  never has to invent a label;
- a history summary — booking counts per facility and per weekday, the
  resident's most frequent facility and preferred hour, their last facility,
  their median inter-booking gap and median lead time, and a behaviour-change
  flag;
- the most recent bookings in full, oldest to newest.

Every summary the shared feature module already computes is **imported**, not
recomputed. The LLM track defines no target, no split, no tolerance, and no
metric of its own; a test fails if it tries.

Prompts measured **2,539 / 2,618 / 2,681 characters** at the 50th, 90th, and
99th percentiles on the training split, about 1,400–1,450 tokens.

### Decoding

Answers are generated under a frozen JSON schema with Outlines, greedy at
temperature zero. A completion that fails to parse or validate is retried
once, deterministically; a second failure becomes a **typed failure** that
keeps its place in every denominator with all four components counted wrong.
It is never replaced by a guess, a baseline value, or a repaired answer.

Before any scored generation, the pinned stack was made to answer **100
compatibility fixtures**: 100 valid, 0 retried, 0 failed, and 10 of those
decoded a second time byte-identically.

**A real defect was found here and fixed.** The chat template renders an
assistant turn as `<think>\n\n</think>\n\n` followed by the answer, and
prompt masking stopped before that prefix — so training taught the model to
emit it, while constrained decoding starts at the answer's first byte and
forbids it. Training and inference did not agree on the response format.
The decoder now derives that prefix from the chat template itself and
supplies it before the schema takes over, and the prefix is part of the run
identity, so a run with it is a different experiment from one without.
Re-scoring with the formats aligned changed the adapted pass's bucket
accuracy and notification match by **0.000** — the defect was real, and the
hypothesis that it explained the model's behaviour is disproven rather than
open.

### Training

LoRA adapters on the top 16 blocks of the 4-bit base, `q/k/v/o/gate/up/down`
projections, rank 8, scale 20, learning rate 1e-4, Adam, batch size 1 with
four-step gradient accumulation, loss taken on **answer tokens only**. The
base weights stay quantised and never receive a gradient. Seeds are fixed
and recorded; the trainer's configuration is written beside the adapter and
hashed.

**How large the full run was allowed to be was decided on timing alone,
before any quality number existed.** A four-step ladder was projected from
the pilot's measured seconds-per-iteration against the shared 4-hour
unattended-compute cap, and the first step that fit was sealed:

| Step | Rows | Passes | Iterations | Projected total | Fits |
|---|---|---|---|---|---|
| 1 | 2,000 | 3 | 6,000 | 12.70 h | no |
| 2 | 2,000 | 2 | 4,000 | 9.08 h | no |
| 3 | 2,000 | 1 | 2,000 | 5.45 h | no |
| 4 | 1,000 | 1 | 1,000 | **3.64 h** | **yes** |

The full run trains at step 4 and refuses any other size. Only the adapter
parameters train, and the saved adapter is reloaded through the scored
generation path before it is used, so an adapter the runtime cannot load is
caught at training time rather than at scoring time.

### The learnability gate, and its removal

Before spending the full training budget, a gate compared a small 400-iteration
pilot adapter against the base model zero-shot on a frozen, stratified 200-row
validation manifest. Both passes answered the same rows, so the comparison is
paired.

The pilot improved on zero-shot by more than sampling noise on both gated
metrics — bucket accuracy **+0.095 [+0.055, +0.140]** and notification match
**+0.115 [+0.070, +0.165]**. But the gate also required neither metric to
fall below a simple reference, and the pilot's notification match of **0.125**
sat under the **0.145** of a rule that answers the training median delay for
every row. The branch stopped there on 2026-08-15.

**That blocking condition was removed on 2026-08-16 at the project owner's
explicit direction.** It is recorded as their decision. Three measurements
taken at the time say why it is defensible rather than merely permitted:

- the shortfall the gate fired on is **−0.020 with a paired 95% interval of
  [−0.095, +0.050]** — indistinguishable from zero, and resting on 54
  discordant rows out of 200;
- the reference rule scores **0.145 on those 200 rows but 0.111 on all 3,437
  validation rows**. The manifest is stratified by prior-booking count, so the
  bar the gate set was a property of that draw rather than a population value;
- the delay target is the gap to a resident's next booking, which is
  **memoryless within a resident** (coefficient of variation 1.09). A
  predictor that knew every resident's true booking rate would reach about
  **0.163**. The gate was trying to resolve a five-point band with a
  ±4.4-point ruler.

The gate still runs and still publishes every number it ever published. It
reports; it no longer stops. The obligation it was protecting is unchanged
and is honoured below: a result that loses to the shared baseline is reported
as a loss, and carries a recommendation against the LLM rather than another
round of tuning.

### What the pilot showed, and what remains untested

The pilot collapsed to a **constant predictor**: all 200 rows received the
same label, `M20658_30461`, and its 0.105 bucket accuracy is that label's
prevalence on those rows. A later, larger diagnostic — 2,000 rows over one
pass, 3.87 hours — did **not** fix it; that run scored 0.1875 overall against
the smaller pilot's 0.2188, and its notification match fell to 0.065. More
training made this worse, not better.

Two candidate explanations were identified and **neither has been tested**;
they are listed as open, not as findings:

- **label form.** Each label costs about 9.9 tokens and 15 of the 17 begin
  with the token `M`, so under greedy decoding the first generated token
  carries no information and the model must commit to a long numeric string.
  This is the documented *label length bias*.
- **optimisation.** A majority-class collapse under LoRA at a low trainable
  fraction is a known failure mode; the learning rate is ten times the
  trainer's own default and was never swept.

### The recommendation this produces

Against this problem and this dataset, **do not ship the LLM**. It is beaten
on the holdout by a frequency/recency rule that needs no GPU, no adapter,
and about 25 seconds of the pipeline's runtime, and it costs 4.4 seconds and
1,500 prompt tokens per row to lose.

That recommendation is what the plan requires of a losing result, and it is
recorded rather than answered with another round of tuning. The two untested
explanations above (label form, optimisation) remain untested; naming them is
not a claim that fixing them would change the verdict.

unattended cap is 4 hours; this branch's work took it to roughly 9 hours,
including a 2,000-row diagnostic and this 2h14m full run. The overrun was a
deliberate instruction, and the ladder's own projection had said the run fit
in 3.64 h before a machine-load spike inflated the per-iteration cost.

### Limitations and failure cases

- **Delay prediction is close to a dead end here, for any model.** The target
  is the gap to a resident's next booking, and within a resident that gap is
  memoryless (coefficient of variation 1.09). A predictor knowing every
  resident's true rate reaches about 0.163; a single constant reaches 0.111.
  The whole winnable band is about five points wide.
- **The adapter is nearly a constant predictor on delay.** Two labels out of
  seventeen across 500 rows. Training more made it worse, not better.
- **Only one configuration was trained at full size.** No learning-rate,
  rank, or label-form sweep was run, so this is a result about *this*
  configuration and not about what a fine-tuned 4B model can do here.
- **Leakage is asserted, not proven, for this branch.** Prompts are built
  from bookings at or before each row's origin and carry no target, and the
  scored pass cannot read a target before its answers are hashed. That is an
  enforced ordering, not a property test.

### Reproducing this

```
make llm-reproduce
```

Replays the committed answers, recomputes every rate, re-renders the
workbook, and asserts the result. **No GPU, no adapter load, no API key** —
the committed generation cache is the mechanism. It checks that the answers
on disk still hash to the frozen value, that every sealed row has an answer,
that no answer was dropped or substituted, and that all four rates and the
operational numbers recompute exactly.

To regenerate rather than replay, on Apple Silicon:

```
make up
python -m facility_prediction.cli llm-tier-b    # ~2 h
python -m facility_prediction.cli llm-final     # ~0.6 h
```
